# Crypto Price Tracker — Project Specification

**Status:** Draft for implementation  
**Audience:** Product owner and engineering team  
**Scope:** Small, single-user CRUD application with a web GUI and Coinbase spot prices

## 1. Purpose

Build a small web application that lets a user maintain a list of crypto products and view their latest Coinbase prices in a GUI. Prices refresh periodically and can also be refreshed on demand. The application runs locally using Terraform-managed Docker containers.

## 2. Goals and non-goals

### Goals
- On first run, fetch a starter catalog from Coinbase and initialize exactly 10 supported crypto spot markets as tracked products.
- Create, view, edit, and delete those tracked products in the application; allow replacing deleted products from the Coinbase catalog.
- Display the latest available Coinbase spot price for each active product, with currency and update time.
- Refresh prices on a configurable interval and on user request.
- Make provider failures and stale data visible rather than presenting them as current.
- Make the application straightforward to start and test through Docker.
- Provide automated unit, integration, and UI/API acceptance coverage.

### Non-goals for the first release
- Trading, order placement, portfolio balances, or wallet connectivity.
- User accounts, authentication, authorization, or multi-tenant access.
- Historical price charts, alerts, or persisted price history.
- Arbitrary exchanges or market data providers beyond Coinbase.
- Financial advice or guaranteed real-time/executable pricing.

## 3. User stories

1. As a user, I can see all tracked products and their latest prices in one screen.
2. As a user, I start with 10 crypto spot markets discovered from Coinbase and can add a supported market from the Coinbase catalog by selecting its product ID.
3. As a user, I can edit a product's display name, Coinbase product ID, quote currency, and active state.
4. As a user, I can remove a product I no longer track, after confirming the action.
5. As a user, I can tell when a price was last updated, is unavailable, or is stale.
6. As a user, I can request an immediate refresh and see a clear result.

## 4. Terminology and product model

A **tracked product** is an application record describing one Coinbase market to display. The Coinbase product ID identifies the market, commonly as `BASE-QUOTE` (such as `BTC-USD`). The quote currency is explicit or derived from the product ID and must agree with the selected Coinbase market.

Suggested fields:

| Field | Type | Rules |
|---|---|---|
| `id` | UUID or integer | Generated by the application; immutable |
| `name` | string | Required; trimmed; 1–80 characters |
| `coinbase_product_id` | string | Required; uppercase canonical form; valid supported Coinbase product |
| `quote_currency` | string | Required; 3–10 characters; must match product ID quote component |
| `is_active` | boolean | Defaults to true; inactive products are retained but not refreshed |
| `created_at` | timestamp | Set by the application, UTC |
| `updated_at` | timestamp | Set by the application, UTC |

The initial tracked list is bootstrapped to 10 distinct, supported Coinbase spot markets on first run. The Coinbase product catalog is discovery data; the tracked product records are application-owned and editable/deletable. Deleting a tracked product does not delete it from Coinbase. The combination of Coinbase product ID and quote currency must be unique. For the initial release, only products whose Coinbase market can be queried by the configured Coinbase public market-data endpoint are supported. The UI should validate format locally; the server/provider check is authoritative. Do not assume a syntactically valid market exists.

## 5. Functional requirements

### 5.1 Coinbase catalog and product CRUD
- On first database initialization, fetch Coinbase spot products and seed 10 distinct supported crypto markets as tracked application records. Prefer a configured deterministic list of common USD markets; if a preferred market is unavailable, choose the next eligible USD spot market from the Coinbase catalog in deterministic product-ID order. Never depend on Coinbase response order.
- Filter out non-spot, offline, non-crypto, and unsupported markets. If Coinbase provides fewer than 10 eligible products or its catalog cannot be reached, keep the application available, report bootstrap status, and allow retry; do not seed fake products.
- Store Coinbase product ID, base/quote currencies, and a display name from Coinbase metadata where available. The user may edit the application display name.
- Provide catalog search/selection so a user can add supported Coinbase products after deleting or deactivating an existing product. Existing tracked products must not be overwritten when catalog data refreshes.
- List products, showing name, market ID, active state, latest price state, and last successful update time.
- Create a product with required fields and actionable validation errors.
- Read one product's details (or expose equivalent detail in the list/edit form).
- Update editable fields. Revalidate uniqueness and market support.
- Delete a product. Require confirmation in the GUI. A deleted product is no longer returned or refreshed.
- Inactive products remain visible but do not trigger price requests; their existing price may be displayed with an inactive indicator.
- Handle empty state with a clear prompt to add the first product.

### 5.2 Price retrieval and display
- Retrieve spot prices from Coinbase using the official public market-data interface selected by implementation (document the exact endpoint/API version in the implementation README).
- Keep provider access behind a small adapter/service so API details can be changed without changing CRUD or GUI logic.
- Display decimal prices without binary floating-point rounding. Store/transport prices as decimal strings or a decimal type; do not use floating-point arithmetic for monetary values.
- Display quote currency, retrieval timestamp, and state: `current`, `stale`, `unavailable`, or `not fetched`.
- Do not represent a failed request as a zero price. Retain and clearly mark the last successful price if a later refresh fails.
- A successful update must only replace the displayed price after a valid, positive provider price has been parsed.
- Apply sensible request timeouts, bounded retries for transient failures, and provider rate-limit handling. Avoid a retry storm; use backoff and surface the failure.
- Price requests should be batched only if the chosen Coinbase endpoint supports it. Otherwise enforce a concurrency limit and handle per-product outcomes independently.

### 5.3 Periodic refresh
- Refresh active products on a configurable server-side interval. Default: **60 seconds**; minimum configurable interval: **15 seconds**, unless Coinbase limits or deployment constraints require a higher minimum.
- Provide a manual “Refresh now” action. Prevent overlapping refresh cycles for the same product.
- Refresh status and data must not depend on a browser tab remaining open.
- Make refresh interval configurable through environment/configuration and document the setting.
- On startup, perform an initial refresh of active products, subject to provider limits.

### 5.4 GUI behavior
- Provide a responsive dashboard with an accessible products table/list and create/edit/delete controls.
- Show loading, empty, success, validation, and provider error states.
- Keep the page usable if one product fails while others succeed.
- Update displayed prices after a refresh without requiring a full page reload (polling or server push is an implementation choice).
- Use semantic labels, keyboard-operable controls, and readable contrast.

## 6. Quality and operational requirements
- Small, maintainable separation between UI, application/API logic, persistence, and Coinbase adapter.
- Persist product records across container restarts using a Docker-managed volume. PostgreSQL is the selected datastore for local development and deployment; Terraform manages the persistent local PostgreSQL volume.
- Keep secrets out of source control. Public price reads should not require credentials where Coinbase supports unauthenticated access. If credentials become necessary, use environment variables and never log them.
- Use structured application logs; do not log secrets. Include product ID and failure category where useful.
- Provide health/readiness endpoint(s) suitable for Docker health checks.
- Handle graceful shutdown of refresh scheduling and database connections.
- Pin or constrain runtime/dependency versions appropriately; document supported runtime and Docker requirements.
- No claim that displayed prices are guaranteed live, complete, or suitable for execution. Show source and last-updated time.

## 7. Suggested architecture

Keep the implementation intentionally small:

1. **Web UI** — dashboard and product forms.
2. **Application/API layer** — CRUD validation, refresh commands, response shaping.
3. **Persistence** — products and optionally latest quote/status, with managed PostgreSQL schema setup.
4. **Coinbase adapter** — HTTP client, timeout/retry/rate-limit handling, response validation.
5. **Refresh scheduler** — one server-side scheduler invoking the same refresh service as manual requests.

The first release uses a React UI, one FastAPI application, one price-refresh worker, and PostgreSQL. Avoid adding a queue or more services unless a concrete requirement needs them. Persist only the latest quote per product; price history is out of scope.

## 8. API contract (implementation-neutral example)

Use versioned REST/JSON routes.

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/api/v1/products` | List tracked products with latest quote/status |
| `GET` | `/api/v1/coinbase/products?search=` | Search eligible Coinbase catalog products not already tracked |
| `GET` | `/api/v1/bootstrap` | Read initial catalog bootstrap status and seeded count |
| `POST` | `/api/v1/bootstrap/retry` | Retry incomplete first-run bootstrap |
| `POST` | `/api/v1/products` | Create product |
| `GET` | `/api/v1/products/{id}` | Read product |
| `PATCH` | `/api/v1/products/{id}` | Update product |
| `DELETE` | `/api/v1/products/{id}` | Delete product |
| `POST` | `/api/v1/prices/refresh` | Trigger refresh for active products |
| `GET` | `/api/v1/health/live` | Liveness check |
| `GET` | `/api/v1/health/ready` | Readiness check, including persistence availability |

Suggested list item:

```json
{
  "id": "generated-id",
  "name": "Bitcoin",
  "coinbase_product_id": "BTC-USD",
  "quote_currency": "USD",
  "is_active": true,
  "price": "65000.12",
  "price_status": "current",
  "price_as_of": "2026-10-09T10:00:00Z"
}
```

Use appropriate status codes: `201` create, `200` read/update/refresh accepted or completed, `204` delete, `400` malformed input, `404` missing record, `409` duplicate market, `422` validly formed but unsupported market/field validation, and `502`/`503` provider unavailable where the request is synchronous. A background refresh should report per-product outcomes rather than fail the whole batch because one product failed. Return a consistent error body with a stable machine-readable code and human-readable message. Do not expose provider credentials or raw internal stack traces.

## 9. Persistence and data behavior
- Products must persist through app/container restarts.
- Latest quote may be persisted with `price`, `price_as_of`, and `price_status` fields, or stored separately as one current quote per product.
- A product deletion removes its associated current quote. Historical price retention is not required.
- Schema setup and changes must be documented and applied explicitly.
- Store timestamps in UTC and render them in the user's local timezone in the GUI.

## 10. Docker and local developer experience

Deliver:
- `Dockerfile` using a small production-appropriate base image and non-root runtime where practical.
- Terraform configuration defining the application containers, persistent data volumes, environment configuration, port mapping, and health checks.
- `.dockerignore` excluding VCS metadata, local virtual environments, caches, secrets, and generated artifacts.
- `.env.example` containing documented non-secret configuration only.
- README commands for build/start, stop, logs, tests, and removing the local data volume (with a clear data deletion warning).

Expected developer flow (adapt names/ports to the implementation):

```sh
terraform -chdir=terraform init
terraform -chdir=terraform apply
# Open the documented local URL
terraform -chdir=terraform destroy
```

The app must bind to `0.0.0.0` inside its container. Data must survive normal container restarts; Terraform destroy deletes the named volume and data.

## 11. Configuration

Document at least:

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | implementation-defined | HTTP listen port |
| `DATABASE_URL` | PostgreSQL connection URL | Persistent application database |
| `PRICE_REFRESH_INTERVAL_SECONDS` | `60` | Periodic refresh interval; validate minimum |
| `COINBASE_REQUEST_TIMEOUT_SECONDS` | `8` | Provider request timeout |
| `PRICE_STALE_AFTER_SECONDS` | `180` | Age after which a last successful quote is marked stale |
| `LOG_LEVEL` | `info` | Logging verbosity |

If the Coinbase endpoint requires configuration or credentials, list the setting explicitly and provide no real credentials in `.env.example`.

## 12. Test plan and acceptance cases

Automated tests must not call live Coinbase in the default test suite. Inject/mock the provider adapter and use deterministic fixtures. Add a small optional manual smoke-test procedure for live Coinbase connectivity. Tests should run both in the documented local workflow and in the Docker environment (or via a documented test service/command).

### Unit tests
1. Product input trims name, canonicalizes product ID, and rejects missing/overlong/invalid fields.
2. Product market ID and quote currency must agree.
3. Duplicate product market IDs are rejected consistently, including concurrent create attempts if relevant to the datastore.
4. Price parser accepts a valid positive decimal and preserves precision.
5. Price parser rejects missing, malformed, zero, negative, NaN, and infinite values.
6. Quote status is `stale` once age exceeds configured threshold and `current` before it.
7. Failed refresh retains last successful price and records failure/stale state; it never substitutes zero.
8. Inactive products are excluded from refresh selection.

### API/integration tests
1. List returns an empty collection on a new database.
2. Create valid product returns `201`, persists fields, and appears in list.
3. Create invalid product returns a validation error and does not persist data.
4. Duplicate Coinbase market returns `409` and does not create a second record.
5. Read returns the expected product; unknown ID returns `404`.
6. Update changes supported fields and persists them; invalid update is rejected without partial mutation.
7. Delete removes the product and associated current quote; deleting an unknown ID returns `404`.
8. Refresh success stores/displays returned price, currency, and timestamp.
9. Provider timeout, rate limit, malformed response, and server error are handled without crashing; unaffected products still refresh.
10. Manual refresh and scheduled refresh share behavior and do not overlap for a product.
11. Health is live when the process is running; readiness fails when required persistence is unavailable.
12. Database schema setup on an empty database succeeds and app can restart with product records intact.

### GUI/end-to-end acceptance tests
1. Dashboard shows the empty state and create action when no products exist.
2. User creates a product and sees it in the list with a loading/not-fetched state until a quote is available.
3. With a mocked successful quote, the dashboard shows correctly formatted price, quote currency, and local update time.
4. User edits product details and sees the changes after reload.
5. User attempts a duplicate/invalid market and sees a clear inline error; existing data remains unchanged.
6. User deletes a product only after confirmation; it disappears after confirmation and remains after cancel.
7. Manual refresh updates a price and communicates completion/failure.
8. Provider failure for one market is visible for that row while successful rows remain usable.
9. Stale quote is visually distinguishable and includes its last successful update time.
10. Core create/edit/delete/refresh flows can be operated using keyboard navigation.

### Docker acceptance tests
1. `terraform -chdir=terraform apply` starts the service and health check passes.
2. GUI is reachable on the documented host port.
3. Product create, restart, and list demonstrate persistence in the named volume.
4. Logs and shutdown are clean; missing provider connectivity does not prevent CRUD or service startup.
5. Test command is documented and passes with provider calls mocked.

## 13. Definition of done
- All requirements in sections 5 and 10 are implemented or explicitly recorded as deferred with rationale.
- Product CRUD and latest-price display work end to end.
- Periodic and manual refresh work, with clear stale/unavailable states.
- Automated tests cover the specified validation, persistence, provider failure, and user flows.
- Docker build and startup are documented and repeatable; product data persists across restarts.
- README documents architecture, endpoint/market assumptions, configuration, test commands, and known limitations.

## 14. Decisions to confirm during implementation
These are deliberately left open because no language/framework or deployment constraints were provided:
- UI and backend framework/language.
- Current Coinbase endpoint availability/rate-limit behavior in the target deployment.
- Whether the preferred initial 10-market list should be configurable by environment or application settings.
- Whether price state should be persisted across restart or simply refetched on startup.
- Target browser support and visual design direction.
